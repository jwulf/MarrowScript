# MarrowScript Phases 14–22 — LLM Cognition Polish & Production Surface

This chapter documents the 9 phases that landed after the initial LLM harness (Phases 1–13). Each is purely additive — a system that doesn't opt in compiles bit-for-bit unchanged. The features compose; you can adopt them one at a time.

## Document conventions

For each phase:
- **Surface** — what the user writes
- **Compile-time guarantees** — what the type checker enforces (error codes)
- **Runtime artifacts** — files emitted, conditional on opt-in
- **CLI** — new subcommands when relevant
- **Migration** — what changes for systems that don't use the feature (answer: nothing)

Error code ranges:
- T029 — Phase 15 (tools)
- T030–T034 — Phase 16 (evaluation)
- T040–T043 — Phase 17 (checkpoint)
- T050–T054 — Phase 21 (cost budgets)
- T060–T063 — Phase 18 (promptbook)
- T070–T071 — Phase 19 (cost-aware routing)

## Phase 14 — Multi-file artifact output

### Surface

Prompts may declare a `File` or `list<File>` return type:

```marrow
prompt generate_module(spec: string) {
  router: forge_router
  template: "extension_point:tmpl_generate_module"
  returns: list<File>
  validate: ast_compiles
  on_invalid: retry_with_repair_prompt
}
```

`File` is a built-in record:
```
File { path: string, content: string, kind: optional<string> }
```

### Compile-time guarantees
- Type checker registers `File` as a built-in entity at the start of every system check, so `returns: File` and `returns: list<File>` resolve without user-side `entity File { ... }`.

### Runtime
- `parseModelOutput` dispatches on shape: `"file"` returns one record, `"files"` returns an array. Tolerates bare arrays, `{ files: [...] }` envelopes, and single-record-to-list promotion.
- `validateSchemaOnly` rejects empty paths, path-traversal (`..`), absolute paths, empty content, non-string `kind`, duplicate paths, empty lists.
- `validateAstCompiles` dispatches: string → legacy TS validator, single File → forwards `.content`, list of Files → validates `.ts/.tsx/.cts/.mts` only with file-prefixed issue messages.

### Migration
None. Existing prompts with `returns: string` continue compiling unchanged.

## Phase 15 — Bounded tool calls (`tools:` becomes real)

### Surface

```marrow
capability search_docs(query: string, max: uint) {
  cognition: vector_retrieve using { task: query, k: max }
  returns: string
  sync: eventual
}

prompt classify_with_lookup(question: string) {
  model: Tiny
  template: "extension_point:tmpl_classify"
  returns: string
  validate: schema_only
  tools: [search_docs]
}
```

### Compile-time guarantees
- **T029**: tool capabilities must be cognition-bearing (declare `cognition: <primitive>`). Effect-bearing or pipeline capabilities can't be tools.
- The closed list pairs with T023 (existing) for namespace check.

### Runtime
- Provider protocol gains `ChatToolSpec`, `ChatToolCall`, `tool` role on `ChatMessage`, `tools?` / `tool_choice?` on `ChatRequest`, `tool_calls?` on `ChatResponse`.
- OpenAI-compat adapter forwards tools as canonical function-calling shape; drops `response_format` when tools are present.
- `__TOOL_SPECS` (JSON-Schema typed list) and `__TOOL_DISPATCH` (per-tool runCognition invoker) emitted into `prompts.ts`.
- `__chatWithTools` runs the bounded loop. Cap: `LLM_TOOL_CALL_MAX` (default 5). Past the cap throws `ToolCallBudgetExceeded`.
- Per-tool `kind: "tool_call"` child spans with `step: tool:<name>`, args, result, latency, status.

### Counters
`cognition.tool_calls{prompt, tool, status}`, `cognition.tool_call_budget_exceeded{prompt, model}`.

### Migration
None. Prompts without `tools:` keep their existing direct-chat path bitwise-unchanged.

## Phase 16 — `evaluation` primitive

### Surface

```marrow
evaluation generate_quality {
  prompt: generate_artifact

  cases: [
    {
      name: "simple"
      input: { description: "...", complexity: 0.5 }
      expected: {
        passes: ast_compiles
        contains_class_named: "^[A-Z][a-zA-Z]+Adapter$"
        max_lines: 400
        must_contain_string: ["export"]
      }
    }
  ]

  metric: pass_rate
  baseline: { min_pass_rate: 0.85 }
  schedule: { on: ["pre_commit", "ci_pr"] }
}
```

### Closed expectation operators (8)
- `passes: ast_compiles | schema_only`
- `contains_class_named: <regex string>`
- `must_contain_string: list<string>`
- `must_not_contain_string: list<string>`
- `imports_only_from: list<string>` (allowlist; relative imports always allowed)
- `max_lines: uint`
- `min_lines: uint`
- `latency_under_ms: uint`

### Compile-time guarantees
- **T030**: undeclared prompt
- **T031**: empty cases / nameless case
- **T032**: case input binds unknown prompt parameter
- **T033**: `passes: ast_compiles` on non-string return type (string / File / list<File> only)
- **T034**: duplicate case names within an evaluation

### Runtime / CLI
- `eval/<name>.ts` per evaluation (typed runner with embedded fixtures)
- `eval/index.ts` registry
- `bin/evaluate.ts` CLI: `npx ts-node bin/evaluate.ts [<name>|--list]`
- Each runner persists `eval/<name>.last.json` so `git diff eval/` surfaces regressions.
- Exit codes: `0` baseline ok, `1` regression, `2` runtime error.

### Migration
None. Systems without `evaluation` declarations emit no eval files.

## Phase 17 — Flow checkpoint primitive

### Surface

```marrow
flow patch_review {
  step generate: run_patch(d)
    checkpoint: review_plan {
      shows: [d.body, d.id]
      allow: ["approve", "edit", "regenerate", "reject"]
      timeout: 24h
      on_timeout: cancel
    }
  step apply: save_patch(d)
    compensate: rollback_patch(d)
}
```

Compensate and checkpoint clauses can appear in either order.

### Decisions (closed list, v1)
`approve | reject | edit | regenerate | cancel`

### Compile-time guarantees
- **T040**: empty `allow:` list (deadlock by construction)
- **T041**: `timeout: 0s` (meaningless wait)
- **T042**: duplicate checkpoint name within a flow
- **T043**: unsupported decision string

### Runtime
Three emitted files when at least one flow has a checkpoint:
- `migrations/flow_runs.sql` — `flow_runs` (state machine: `running | paused | resumed | completed | cancelled | failed`) + `flow_run_checkpoints` (decision audit)
- `src/flows/checkpoints.ts` — 10 documented exports: `startFlowRun`, `pauseFlowRun`, `awaitDecision`, `submitDecision`, `markRunCompleted`, `markRunFailed`, `markRunCancelled`, `markRunResumed`, `getFlowRunWithPending`, `buildShowsPayload`. Includes in-process `Map<flow_run_id+checkpoint, resolver>` for instant resume.
- `src/routes/flow_runs.ts` — `GET /flow_runs/:id` + `POST /flow_runs/:id/checkpoint/:name` with compile-time `ALLOW: Record<flow:checkpoint, string[]>` enforcement.

### Counters
`flow.run_started{flow}`, `flow.paused{checkpoint}`, `flow.checkpoint_decided{checkpoint, decision}`, `flow.checkpoint_timeout{checkpoint}`, `flow.run_completed{}`, `flow.run_failed{}`, `flow.run_cancelled{}`.

### Cross-process resume
v1 in-process only. v2 (future) adds `LISTEN`/`NOTIFY` polling on Postgres. The persistence layer is correct in the meantime.

### Migration
None.

## Phase 18 — Promptbook standard library

### Surface

```marrow
prompt is_spam(text: string) {
  model: Tiny
  promptbook: binary_classify
  with: {
    positive_label: "spam"
    negative_label: "ham"
  }
  returns: string
  validate: schema_only
}
```

`promptbook:` and `template:` are mutually exclusive.

### Closed registry (8 entries)

| Category | Entries |
|---|---|
| Classification | `binary_classify`, `multi_class_classify` |
| Generation | `summarize`, `paraphrase`, `translate` |
| Extraction | `extract_json` |
| Reasoning | `chain_of_thought_solve`, `self_critique_then_revise` |

Each entry declares typed parameters (string / string[] / uint / float; required + optional) and a baseline template with `{{<param>}}` placeholders for promptbook args and `{{__input.<name>}}` placeholders for prompt-call inputs.

### Compile-time guarantees
- **T060**: `template:` and `promptbook:` both declared
- **T061**: unknown promptbook entry (error message lists all allowed)
- **T062**: missing required arg for the entry
- **T063**: unknown arg name (error message lists allowed)

### Lowering
Templates are rendered at compile time:
- string args → literal substitution
- string[] args → bullet list (`  - x`)
- numeric args → `String(value)`
- missing optional args → empty string
- `{{__input.<name>}}` placeholders preserved for runtime substitution

The lowered `IRPrompt.template` is a plain string — the runtime has no dependency on the promptbook module.

### Migration
None. Existing prompts using `template:` continue working.

## Phase 19 — Cost-aware routing

### Surface

```marrow
router smart_router {
  by: input.complexity
  observe: ["validation_pass_rate", "latency_p95_ms", "cost_usd_per_call"]

  tier easy { max: 0.6 -> Tiny }
  tier hard { -> Medium }

  policy: minimize_cost_subject_to {
    validation_pass_rate >= 0.9
    latency_p95_ms <= 30000
  }

  fallback: Medium
}
```

### Closed metric vocabulary (7)
`validation_pass_rate`, `latency_p50_ms`, `latency_p95_ms`, `cost_usd_per_call`, `calls`, `tokens_per_call`, `confidence_mean`.

### Compile-time guarantees
- **T070**: `observe:` entry or constraint metric not in `KNOWN_METRICS`
- **T071**: policy constraint references a metric not in `observe:` (would be unverifiable)

### Runtime
Decision logic stays static — the runtime still picks tiers via the existing `parseByExpr` lookup. Phase 19 ships the *intent* surface; the router's deterministic compile-time decision table is preserved.

### CLI (Phase 19 v2)
`marrowc tune-router <name> --spec <file.marrow> --traces <dir> [--json]`

Aggregates recorded cognition trace dumps and reports per-tier metrics against the declared policy. Patterns surfaced as suggestions:

1. **Low call volume** — fewer than 30 calls observed for a failing tier; collect more traces before re-tuning.
2. **Failing tier vs passing later tier** — suggests lowering the higher tier's `max:` so easy work routes there too.
3. **Cheap tier passes everything** — when a tier with ≥50 calls meets every constraint, suggests raising its `max:` to capture more traffic.

Exit codes: `0` all constraints pass, `1` at least one constraint fails. The .marrow source stays the source of truth — the tuner never rewrites it.

### Migration
None. Routers without `observe:` or `policy:` keep bit-for-bit existing behavior.

## Phase 20 — Code-spec sync (v1: AST-only)

### CLI

```
marrowc reflect <project_dir> [--out <file>] [--system <name>]
marrowc diff-spec <spec.marrow> <project_dir>
```

### Reflect
Walks a TypeScript project recursively (skipping `node_modules`, `dist`, `build`, dot-prefixed dirs, and `.d.ts` files), finds class/interface declarations with an `id` member, and emits a stub `.marrow` source.

### Type projection rules
| TypeScript | MarrowScript |
|---|---|
| `string` | `string` (or `uuid` when field name is `id`) |
| `number` | `float` (conservative — no int/float guessing) |
| `boolean` | `bool` |
| `Date` | `timestamp` |
| `any` / `unknown` / `Record<string, unknown>` | `json` |
| `T[]` / `Array<T>` | `list<T>` |
| `Buffer` / `Uint8Array` | `bytes` |
| `x?:` (optional member) | `optional<T>` in stub |

Ontology fields (`id`, `created_at`, `updated_at`) are NOT re-declared in the stub — the type checker adds them automatically.

### Diff-spec
Compares an existing `.marrow` spec's entity declarations against the source-derived shape. Reports per-entity additions, removals, and field-level type changes. Exit non-zero on any drift — drops cleanly into CI as a schema-drift gate.

### What v1 doesn't do
LLM-driven inference for capabilities, state machines, and audit boundaries is documented as v2. The static analysis is the foundation; the LLM driver lands cleanly on top of it once the cognition runtime is available outside a generated project.

### v2: LLM-driven capability inference (DELIVERED)
`marrowc reflect-llm <project_dir>` prompts an LLM via a closed 5-tool list (`list_directory`, `read_file`, `find_class`, `find_function`, `find_references`) to walk the project and infer capabilities operating on the entities the v1 static analysis found. The model reads code, observes function signatures and bodies, and reports structured JSON with `name`, `entity`, `params`, `effects`, `requires`, `source_file`, `source_line`, and `confidence`. The output is merged with the v1 entity stub into an enriched `.marrow` source that the reviewer merges.

Architecture (5 files, all under 260 lines): `reflect_llm/types.ts`, `reflect_llm/tools.ts`, `reflect_llm/llm.ts`, `reflect_llm/output.ts`, `reflect_llm.ts`. FakeProvider enables fully offline deterministic testing (41 tests).

### Migration
None. New CLI surface; existing `marrowc compile` unchanged.

## Phase 21 — Cost budgets

### Surface

```marrow
policy app_costs {
  rate_limit: 60 per 1m
  audit: true
  cost_budgets: [
    {
      scope: per_tenant
      window: 1d
      cap_usd: 5.00
      on_exceeded: { action: throttle, retry_after: 1h }
    }
    {
      scope: per_user
      window: 1h
      cap_tokens: 100000
      on_exceeded: { action: error, code: "DAILY_LIMIT" }
    }
    {
      scope: per_feature: "forge_artifact"
      window: 1h
      cap_calls: 10
      on_exceeded: { action: error }
    }
  ]
}
```

### Scopes (closed list)
`per_tenant` | `per_user` | `per_feature: "<capability>"`

### Caps (exactly one per budget)
`cap_usd` (float) | `cap_tokens` (uint) | `cap_calls` (uint)

### Actions (closed list)
- `error` — throws `BudgetExceededError`; `code` field surfaces in the error response
- `throttle` — throws `BudgetThrottleError`; required `retry_after` populates the `Retry-After` hint

### Compile-time guarantees
- **T050**: zero or multiple caps (must be exactly one)
- **T051**: per_feature without feature name OR referencing undeclared capability
- **T052**: `action: throttle` without `retry_after`
- **T053**: window must be > 0
- **T054**: cap values must be > 0

### Reserved keywords
Only the ones that don't collide with common identifiers: `cost_budgets`, `cap_usd`, `cap_tokens`, `cap_calls`, `on_exceeded`, `retry_after`, `throttle`, `per_tenant`, `per_user`, `per_feature`. Words like `scope`, `window`, `action`, `code`, `error` stay as Identifier tokens (parsed by string match inside cost-budget bodies). This is the same pattern SQL uses for `LEFT`/`RIGHT`/`KEY`.

### Runtime
Three emitted files when at least one budget is declared:
- `migrations/budget_counters.sql` — `budget_counters` (composite PK `(budget_id, scope_value, window_start)`, cost stored as micros to dodge float drift) + `budget_events` (audit: `exceeded | throttled | reset`)
- `src/policy/budgets.ts` — `BudgetExceededError`, `BudgetThrottleError`, `BUDGETS: BudgetSpec[]` (compile-time literal), `assertWithinBudget(scope, action, charge)` gate, `chargeBudget(scope, action, charge)` post-increment, `getBudgetState(tenantId)` admin read, `resetBudgetForScope(scopeValue, actorId)` admin reset (audited)
- `src/routes/admin_budgets.ts` — `GET /admin/budgets/:tenant_id?` + `POST /admin/budgets/:scope_value/reset`

### Atomic sliding window
`INSERT ... ON CONFLICT (budget_id, scope_value, window_start) DO UPDATE SET ... = ... + EXCLUDED. ...` — PG handles create-or-update atomically. `windowStart()` rounds the current Date down to the nearest `window_ms` boundary so requests within the same hour for `window: 1h` land in the same row.

### Counters
`budget.exceeded{budget, scope, action}`, `budget.charged{}`, `budget.reset{}`. Audit rows in `budget_events` mirror counters for SOC-style requirements.

### Migration
None.

## Phase 22 — Replay-as-test

### CLI

```
marrowc trace-to-test <trace.json> [--out <file>] [--no-assert-outputs]
```

Converts a recorded cognition trace (the JSON shape `marrowc replay <trace_id>` writes) into a self-contained `node:test` regression test. The catch: production LLM systems break in two ways — **model drifts** (Phase 16 evals catch that) or **the surrounding code changes while the LLM behavior stays the same**. Replay-as-test catches the second category by pinning every recorded input → output mapping.

### Generated test shape
- Imports `node:test`, `node:assert/strict`, `callPrompt`, `getModel`
- `beforeEach` saves each referenced model's provider; `afterEach` restores
- Per-model FIFO output queue; stub serves recorded outputs in order. Past the end throws `replay stub for "<model>" exhausted` — silent stale-data drift is impossible.
- Per-`prompt_call` span: `await callPrompt(prompt, recorded_input)` followed by `assert.deepStrictEqual(result, recorded_output)`.
- Trace-level test pins call count, total tokens, total cost (rounded to 6dp + `Math.abs(diff) < 0.0001` tolerance).

### Redaction-aware
Outputs containing `[REDACTED]` (from `@sensitive` field annotations) skip the deep-equal check and verify only that the call succeeded — otherwise every test against a redacted trace would fail.

### `--no-assert-outputs`
Opt-out for non-deterministic outputs where only the call sequence matters.

### Migration
None. Pure offline tooling — no changes to generated code.

## Composing phases

The phases compose cleanly. A real production system might use:

```marrow
system Production {
  // Phase 14
  prompt generate_extension(spec: string) { returns: list<File> ... }

  // Phase 15
  capability search_docs(q: string) { cognition: vector_retrieve ... }
  prompt classify_with_lookup(text: string) { tools: [search_docs] ... }

  // Phase 16
  evaluation generate_extension_quality { prompt: generate_extension cases: [...] }

  // Phase 17
  flow review { step generate ... checkpoint: ...  step apply ... }

  // Phase 18
  prompt is_spam(text: string) { promptbook: binary_classify with: { ... } }

  // Phase 19
  router smart { observe: [...] policy: minimize_cost_subject_to { ... } }

  // Phase 21
  policy budgets { cost_budgets: [...] }
}
```

Phases 20 and 22 are orthogonal CLI tooling — they read the system + traces but don't change the spec.

## Determinism guarantees

Every phase preserves the compile-time determinism property:
- No `Date.now()` / `Math.random()` in any emitter source
- Deterministic ordering: alphabetical for stable surfaces, declaration order where authoring intent matters
- `marrowc verify-determinism` continues passing — re-running compile produces bitwise-identical output

The only non-determinism in the system is at runtime LLM invocation (recorded in `cognition_traces`) and at runtime DB writes (counters, audit rows). Both are wrapped in compensation, validation, retry, and tracing — exactly the primitives MarrowScript already emits for fallible HTTP and DB operations.
